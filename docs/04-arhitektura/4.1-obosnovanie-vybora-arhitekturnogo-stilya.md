# 4.1. Обоснование выбора архитектурного стиля

Система построена из микросервисов за единой точкой входа API Gateway. Сервисы обмениваются событиями через брокер сообщений. Схемы приведены в нотации C4 на уровнях 1 и 2.

Причины выбора стиля:

- предметные области разделены правилами раздела 2: меню и акции, расчет и статусы заказа, оплаты и возвраты, торговый день, связь с кухней, уведомления; каждую область ведет отдельный сервис со своей БД;
- интеграции с внешними системами изолированы в отдельных сервисах: замена кухни, платежного сервиса, облачной кассы или внешней системы лояльности не затрагивает остальные сервисы;
- устройства киоска разделены по требованиям закона 54-ФЗ о контрольно-кассовой технике: терминал оплаты (пинпад) проводит оплату картой через платежный шлюз банка-эквайрера, его слип — не фискальный чек; чек печатает фискальный регистратор, который передает фискальные данные в ОФД; при оплате в мобильном приложении электронный чек формирует облачная касса;
- статус заказа меняется по событиям оплаты и кухни, а получают его табло, киоск, мобильное приложение, панель персонала и внешняя система лояльности; брокер доставляет одно событие всем подписчикам и хранит его, пока получатель недоступен;
- киоск, табло, панель персонала и мобильное приложение Релиза 1 используют один API; клиент Релиза 1 подключается без изменения сервисов;
- меню читают все киоски, а меняется оно редко: кэш меню снимает нагрузку с БД;
- сервисы выпускаются независимо, что нужно для последующего подключения производства, склада и закупок ([раздел 1.2](../01-biznes-trebovaniya/1.2-celi-proekta.md)).

Монолит проще в развертывании, но объединяет в одном выпуске интеграции с терминалом оплаты, кухней и внешними системами и затрудняет подключение новых систем ресторана. Протоколы и технологии приведены в [таблице 4.1](#tablitsa-4-1).

Таблица 4.1 — Протоколы и технологии
{: #tablitsa-4-1 .caption }

| Технология | Где используется | Обоснование |
| --- | --- | --- |
| HTTPS (REST, JSON) | Запросы клиентов к API Gateway, синхронные вызовы между сервисами, интеграции с внешними системами | Поддерживается всеми системами, шифрует трафик. Используется там, где ответ нужен сразу |
| API Gateway (Nginx) | Единая точка входа клиентов | Маршрутизация, TLS, проверка токена, ограничение нагрузки. Клиенты не знают внутреннюю структуру сервисов |
| Web SPA | Киоск, табло, панель персонала | Одно веб-приложение на любом экране, обновление без установки |
| iOS, Android | Мобильное приложение (Релиз 1) | [НФТ-14](../02-trebovaniya/2.4-nefunkcionalnye-trebovaniya.md#nft-14) «Поддерживаемые платформы» |
| AMQP (RabbitMQ) | События заказа, оплаты, возврата, торгового дня и кухни | Доставка события нескольким подписчикам с подтверждением. При нагрузке [НФТ-03](../02-trebovaniya/2.4-nefunkcionalnye-trebovaniya.md#nft-03) «Нагрузочный профиль пилота» потоковая платформа Kafka избыточна |
| SSE (Server-Sent Events) | Статусы заказов на табло, киоске и в мобильном приложении, режим работы киоска | Поток от сервера к клиенту поверх HTTP с автоматическим переподключением. Двусторонний WebSocket не нужен |
| Web Push | Уведомления о сбоях на панели персонала | Уведомление доходит, даже если вкладка панели свернута |
| PostgreSQL | БД сервисов меню, заказов, оплат, торгового дня | Связанные данные и транзакции для денежных операций. У каждого сервиса своя БД |
| Redis | Кэш меню | Быстрое чтение меню киосками |
| Протокол терминала оплаты | Киоск — терминал оплаты (пинпад), терминал — платежный шлюз банка-эквайрера | Пинпад — отдельное устройство в корпусе киоска, протокол задают производитель и банк-эквайрер |
| Драйвер ККТ | Киоск — фискальный регистратор | Печать фискального чека и чека возврата. Фискальный регистратор с фискальным накопителем сам передает данные в ОФД |
| Протокол ОФД | Фискальный регистратор и облачная касса — ОФД | Протокол задает ОФД, данные в ФНС передает ОФД |
| OIDC (Keycloak) | Вход сотрудников, токены устройств | Стандарт авторизации поверх OAuth 2.0. Вход гостя в мобильном приложении выполняет внешняя система лояльности |
| Vault, OpenSearch, Prometheus, Jaeger (OTLP), Grafana | Служебный слой | Секреты, логи, метрики, трассировки и дашборды. Мониторинг нужен для проверки [НФТ-04](../02-trebovaniya/2.4-nefunkcionalnye-trebovaniya.md#nft-04) «Доступность» и [НФТ-13](../02-trebovaniya/2.4-nefunkcionalnye-trebovaniya.md#nft-13) «Доступность приложения» |
